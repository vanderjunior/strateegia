# Project Direction

## Product Direction

- StudyFlow AI is a learning system, not just a quiz engine
- the simulado pipeline should support safe learning feedback
- correctness and scoring must remain separate from runtime mutation
- runtime application must be controlled, explainable, reversible, and user-scoped

## Pedagogical Objectives

- cognitive sustainability
- long-term learning integrity
- confidence calibration
- recovery and rehabilitation after weak performance
- reduction of harmful over-automation
- avoidance of opaque adaptive jumps
- preservation of user trust
- avoidance of punishment loops
- feedback should inform future learning without destabilizing the curriculum

## Runtime Product Philosophy

- suggest first, apply later
- plan before mutate
- policy before apply
- ledger before propagation
- minimal isolated apply before global updates
- avoid aggressive autonomous scheduling
- avoid hidden ranking or retention recalculation
- avoid turning a simulado into uncontrolled curriculum mutation

## Near-Term Direction

- the current chain is complete through Runtime Apply Policy / Feature Flag Foundation
- the next step is `47B Runtime Apply Policy / Feature Flag Stabilization Fixtures`
- then comes `48A Minimal Progress Ledger Apply Foundation`
- `48A` should be the first real apply step, limited to an isolated ledger or snapshot
- `48A` must not apply ranking, retention, scheduler, study cycle, curriculum graph, or adaptive tuning

## Non-Goals

- no LLM runtime autonomy
- no vector or RAG dependency for simulado runtime
- no public answer key or gabarito exposure
- no automatic global curriculum rewrite
- no direct ranking or scheduler mutation from scoring
- no hidden background apply
- no broad refactor during roadmap implementation
